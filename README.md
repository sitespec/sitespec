# Site Spec v0.1 prototype

A runnable prototype of a deterministic, Git-native website system for people and AI agents.

## Implemented

### Spec core

- `site.yaml`, semantic site assets, named navigation collections, `pages/*.yaml`, `components/*/component.yaml`, and a user-owned `shell/`
- JSON Schema Draft 2020-12 validation with AJV
- component registry discovery by convention
- component props as JSON Schema
- `content:` references with no chained refs
- reusable `navigation:` references for named site-wide menus
- provenance-aware content diagnostics
- defaults for variant/theme/page state
- composition rules: archetype, placement, max-per-page
- exactly one declared page-heading section on published non-blank pages
- SEO inheritance and canonical resolution
- internal link validation, including links from published pages to drafts
- `npm run site -- spec [query] --json`
- `npm run site -- validate --json`
- portable agent bootstrap files generated by `sitespec init`: `AGENTS.md` + `CLAUDE.md`
- machine-readable `agent.protocolVersion=1` contract in `npm run site -- spec --json`
- repair-oriented diagnostics with `expected`, `actual`, `allowed`, and `suggestions`
- required v0.1 favicon contract plus optional Apple touch icon and default Open Graph image
- public asset existence/format/path validation
- two-layer design system: primitive values + semantic aliases
- `npm run site -- spec design --json` agent-facing design vocabulary
- deterministic design lint for components and Site Shell (raw color/spacing/typography/radius/shadow, primitive token usage, unknown tokens)
- local web-font contract in `design/fonts.yaml` with `woff2`/`woff`, generated `@font-face`, and no remote font stylesheets

### Controlled component workflow

- `npm run site -- add component <id>`
- safe refusal to overwrite an existing component
- optional semantic role with `--role`
- generated component is valid immediately and visible in the registry
- stable section identity contract:
  - `data-section={sectionId}`
  - `data-component="<id>"`
  - `data-variant={variant}`
  - `data-theme={theme}`
- source contract validation during `npm run validate`
- rendered HTML contract validation during `npm run build`
- `semantics.pageHeading=true` must match exactly one `<h1>` in the implementation
- components that do not declare `pageHeading` may not render `<h1>`
- native `<img>` elements must declare `alt`
- client JavaScript is opt-in with `runtime.javascript: true`
- executable JavaScript in a static component is a validation error

### Vertical build path

- `sitespec init [directory]`
- safe refusal to initialize into a non-empty directory
- starter `hero`, `feature-grid`, `cta`, and `navigation-list` sections
- user-owned Site Shell (`shell/default.astro`, `Header.astro`, `Footer.astro`)
- DTCG-style `design/tokens.json` with strict `primitive` and `semantic` layers
- optional local font-face declarations in `design/fonts.yaml` and `public/fonts/`
- `@sitespec/astro` adapter
- design-token compilation to primitive + semantic CSS custom properties
- generated Astro pages from `ResolvedSite`
- static `npm run build`
- source-oriented `npm run dev` with live validation and Astro HMR
- dev mode includes draft pages and never writes `dist/`
- invalid Site Specs render a self-refreshing diagnostic page without stopping the dev process
- source changes are re-resolved into `.site/astro` without running a production build
- `sitespec dev --json` emits newline-delimited lifecycle events for agents/tools
- production-only `npm run preview` server
- SHA-256 source fingerprint in `.site/build.json`
- stale-build refusal before preview
- static route resolution (`/pricing` -> `dist/pricing/index.html`) with no SPA fallback
- `.site/resolved.json`
- canonical/meta/Open Graph output
- JSON-LD rendering when declared
- `sitemap.xml`
- `robots.txt`
- automatic favicon and optional Apple touch icon injection into `<head>`
- generated section identity attributes (`data-section`, `data-component`, `data-variant`, `data-theme`)
- post-build validation of actual generated HTML
- GitHub Pages deployment adapter with GitHub Actions workflow generation
- GitHub Pages project-site base path support (`https://owner.github.io/repo`)
- post-build rejection of root-relative `href/src` values that bypass a deployment base path
- provider artifact checks for symlinks, hard links, and the 10 GB Pages limit

Not implemented yet: Cloudflare/S3 deployment adapters, asset/image optimization/transforms, font subsetting/transforms, visual regression, dynamic routes/content collections.

## Requirements

Node.js 22+ and npm.

## Product packaging

Core development and website development are intentionally separate.

### Create a normal Site Spec website

The public project-creation flow is:

```bash
npm create @sitespec@latest acme
cd acme
npm run dev
```

`npm create @sitespec` executes the `@sitespec/create` initializer package. It copies the default Site Spec template, pins an exact `@sitespec/cli` version in the site's `devDependencies`, runs `npm install` by default, and initializes Git when available.

Equivalent direct invocation:

```bash
npx @sitespec/create@latest acme
```

A generated website contains only website-owned sources:

```text
acme/
├── site.yaml
├── pages/
├── content/
├── components/
├── shell/
├── design/
├── public/
├── AGENTS.md
├── CLAUDE.md
├── package.json
└── package-lock.json
```

It does **not** contain Site Spec core packages. `package-lock.json` pins the exact engine used by developers, agents, and CI.

Typical website commands are:

```bash
npm run dev
npm run validate
npm run build
npm run preview

npm run site -- spec --json
npm run site -- add component comparison-table
npm run site -- deploy github-pages
```

Agents are instructed to use these project-local npm scripts rather than a globally installed `sitespec` binary.

### Core repository

This repository is the engine monorepo:

```text
packages/
├── core/                  @sitespec/core
├── astro/                 @sitespec/astro
├── template/              @sitespec/template
├── cli/                   @sitespec/cli
└── create/                @sitespec/create

examples/
└── marketing/             workspace playground site
```

`@sitespec/template` is the single source of truth for scaffolding. Both `@sitespec/create` and `sitespec init` use it, so there are not two independent starter implementations.

For core development:

```bash
npm install
npm test

# Run the workspace playground against local workspace packages
npm run dev -w @sitespec/example-marketing
```

For a local scaffold smoke test without publishing packages:

```bash
npm run build
node packages/create/dist/index.js ./tmp-site --no-install --no-git
```

### Versioning boundary

`specVersion: "0.1"` is the website document format. npm package versions are engine releases and are independent. For example, multiple `@sitespec/cli` patch releases may support Site Spec `0.1`. Generated sites pin the CLI exactly rather than using `^` or `latest`.

The v0.1 npm packages use one synchronized release train. Publish dependency order is `@sitespec/core` -> `@sitespec/template` -> `@sitespec/astro` -> `@sitespec/cli` -> `@sitespec/create`. A packaging test prevents those package versions from drifting apart.

### Release process

SiteSpec uses Changesets for versioning and GitHub Actions for npm publishing. User-visible engine changes should include:

```bash
npm run changeset
```

Before a release:

```bash
nvm use
npm install --global npm@11.19.1
npm ci
npm run release:check
```

The release gate tests the monorepo, verifies public package metadata, packs the exact npm tarballs, installs those tarballs into clean temporary projects, scaffolds a website through the packed `@sitespec/create`, and validates/builds the resulting standalone site.

After the initial manual npm bootstrap, `.github/workflows/release.yml` uses npm Trusted Publishing through GitHub OIDC; no long-lived `NPM_TOKEN` is expected. See [`docs/RELEASING.md`](docs/RELEASING.md) for bootstrap and release steps. A committed `package-lock.json` is required before enabling release CI.

## Styling and design tokens

Site Spec pages describe composition, not CSS. The v0.1 design language lives in `design/tokens.json` and has exactly two layers:

```text
primitive values
      ↓
semantic aliases
      ↓
components + shell
```

`primitive` tokens contain literal design decisions. `semantic` tokens must alias primitive tokens and form the stable UI vocabulary. For example:

```json
{
  "primitive": {
    "color": {
      "brand600": { "$type": "color", "$value": "#5b48e8" }
    }
  },
  "semantic": {
    "color": {
      "accent": {
        "default": { "$type": "color", "$value": "{primitive.color.brand600}" }
      }
    }
  }
}
```

The renderer compiles that semantic token to:

```css
--color-accent-default: var(--primitive-color-brand600);
```

Components and `shell/*.astro` may consume `var(--color-accent-default)` but may not consume `var(--primitive-...)` directly. Inspect the current design API with:

```bash
npm run site -- spec design --json
```

`npm run validate` statically rejects styling that bypasses the design system. v0.1 checks raw colors, margin/padding/gap values, font size/family/line-height, border radius, box shadow, unknown design variables, direct primitive-token usage, inline `style=`, local CSS custom-property definitions, and imported component/shell stylesheets. Layout-specific values such as grid fractions, component max-widths, and media-query breakpoints are intentionally not token-enforced in v0.1.

The intended agent workflow is:

- site-wide visual change → edit primitive values or semantic mappings;
- component-specific structure/layout → edit that component while using semantic tokens;
- page-specific allowed presentation → choose `variant` / `theme`;
- never add CSS-like fields to Page Spec.

## Local web fonts

Site Spec v0.1 treats font files as local design assets. `design/fonts.yaml` declares the available `@font-face` records; the actual files live under `public/fonts/`. A fresh project starts with no custom web fonts and uses the system-font primitive from `design/tokens.json`.

Example variable family:

```yaml
specVersion: "0.1"
fonts:
  acme-sans:
    family: Acme Sans
    sources:
      - src: /fonts/acme-sans.woff2
        format: woff2
        weight: "100 900"
      - src: /fonts/acme-sans-italic.woff2
        format: woff2
        weight: "100 900"
        style: italic
```

Defaults are `style: normal` and `display: swap`. v0.1 supports local `.woff2` and `.woff` sources only. Remote font URLs, Google Fonts stylesheets, and hand-written `@font-face` blocks in components/shell are outside the contract and fail validation.

The font face and typography token are intentionally separate. After declaring a local family, update a primitive `fontFamily` token and keep semantic usage stable:

```json
{
  "primitive": {
    "font": {
      "family": {
        "sans": {
          "$type": "fontFamily",
          "$value": "Acme Sans, ui-sans-serif, system-ui, sans-serif"
        }
      }
    }
  },
  "semantic": {
    "font": {
      "family": {
        "body": { "$type": "fontFamily", "$value": "{primitive.font.family.sans}" },
        "heading": { "$type": "fontFamily", "$value": "{primitive.font.family.sans}" }
      }
    }
  }
}
```

Inspect the agent-facing contract with:

```bash
npm run site -- spec fonts --json
npm run site -- spec design --json
```

The Astro adapter generates `.site/astro/src/styles/fonts.css` and imports it globally before token/shell styles. Root-relative font sources are rebased automatically for GitHub project Pages, so `/fonts/acme-sans.woff2` becomes `/repo/fonts/acme-sans.woff2` when `site.url` contains `/repo`.

Font diagnostics include missing/unsafe files, source-format mismatches, unsupported formats, duplicate families/faces/sources, invalid variable weight ranges, and attempts to declare `@font-face` in user Astro code.

## Cross-site navigation and Site Shell

Navigation is a named Site Spec resource, not header markup and not an automatically generated list of pages. Define a collection once in `site.yaml`:

```yaml
navigation:
  primary:
    - id: home
      label: Home
      href: /
    - id: pricing
      label: Pricing
      href: /pricing

  footer:
    - id: privacy
      label: Privacy
      href: /privacy
```

Each item has a stable `id`, a `label`, an `href`, and optional `target: blank`. Internal routes are validated against `pages/*.yaml`; links to draft pages are rejected for global navigation. External `http(s)`, `mailto:`, and `tel:` URLs are allowed.

The renderer does **not** own header/footer presentation. Every generated page is wrapped by the user-owned Site Shell:

```text
shell/
├── default.astro
├── Header.astro
└── Footer.astro
```

`shell/default.astro` receives `site`, `brand`, `page`, and all named `navigation` collections. The starter Header renders `navigation.primary`; the starter Footer renders `navigation.footer` when present and otherwise reuses `navigation.primary`. This means the common “same cross-site menu in header and footer” task needs one collection and no duplicated items. `npm run validate` requires the shell to preserve `<slot />`, but the renderer does not dictate its visual design.

Inspect the shell and navigation contract with:

```bash
npm run site -- spec shell --json
npm run site -- spec navigation:primary --json
```

The same named collection can be reused inside any page section without duplicating menu data:

```yaml
- id: related-navigation
  use: navigation-list
  variant: inline
  props:
    title: Explore
    items:
      $ref: navigation:primary
```

Any custom component can accept the same reference by declaring this prop schema:

```yaml
items:
  $ref: urn:site-spec:0.1:type:navigation
```

This gives one source of truth for cross-site navigation while keeping placement completely independent: header, footer, a sidebar, a page section, or any future shell element can render the same collection.

## Site assets

Site Spec v0.1 keeps raw files in `public/` but gives global assets semantic names in `site.yaml`:

```yaml
assets:
  favicon: /brand/favicon.svg
  appleTouchIcon: /brand/apple-touch-icon.png
  defaultOgImage: /brand/og-default.png

brand:
  logo: /brand/logo.svg
  logoDark: /brand/logo-dark.svg
```

Only `assets.favicon` is required in v0.1. `sitespec init` creates `public/brand/favicon.svg`, so a fresh site is production-valid immediately. The other two asset fields are optional: `appleTouchIcon` is emitted into the document head when present, and `defaultOgImage` becomes the absolute Open Graph fallback when a page does not define `seo.image`.

`brand.logo` and `brand.logoDark` are visual branding and remain the responsibility of the user-owned Site Shell. Favicon and social metadata are document metadata and remain the responsibility of the renderer.

Inspect the machine-facing contract with:

```bash
npm run site -- spec assets --json
```

Global asset references must be safe root-relative paths to real files under `public/`. Validation rejects missing files, dot-segment/path escape attempts, symlinks, and unsupported formats. v0.1 accepts:

- favicon: `.ico`, `.png`, `.svg`
- Apple touch icon: `.png`
- default OG image: `.jpg`, `.jpeg`, `.png`, `.webp`
- brand logos: `.svg`, `.png`, `.jpg`, `.jpeg`, `.webp`

The same root-relative asset path works for GitHub project Pages: the Astro renderer rebases favicon/touch-icon URLs to the deployment base path automatically. Open Graph fallback URLs are resolved as absolute URLs from `site.url`.

Ordinary component/content images stay in typed component props, for example `image.src: /images/product.webp`; v0.1 intentionally does not introduce a global registry for every media file. Asset transforms, responsive image generation, hashing, and optimization are deferred beyond v0.1.

## Component runtime contract

Every Astro section receives:

```ts
{
  sectionId: string;
  variant: string;
  theme: string;
  props: Record<string, unknown>;
}
```

Its section root must preserve the model-to-DOM identity:

```astro
<section
  id={sectionId}
  data-section={sectionId}
  data-component="comparison-table"
  data-variant={variant}
  data-theme={theme}
>
```

This is not cosmetic metadata. It is the stable bridge for validation, visual editing, analytics, browser-based agents, and future DOM-to-Site-Spec navigation.

## JavaScript policy

Components are static by default:

```yaml
runtime:
  javascript: false
```

A component that really needs browser JavaScript must opt in:

```yaml
runtime:
  javascript: true
```

Without that declaration, `<script>` and Astro `client:*` directives fail the component contract. `npm run build` also checks the final HTML for undeclared executable script tags. JSON-LD is not treated as executable client JavaScript.

## Validation boundary

Validation now has two layers:

```text
npm run validate
  -> Site Spec schemas
  -> component prop schemas
  -> composition/semantic rules
  -> Astro source contract

npm run build
  -> everything above
  -> ResolvedSite
  -> Astro static build
  -> final HTML contract
```

The build contract verifies that the renderer actually produced the identity declared by the spec, checks the final page heading count, checks native image `alt` attributes, and catches undeclared client JavaScript.

## Project boundary

The core spec never imports Astro. The flow is:

```text
site.yaml + pages + component contracts + content
  -> @sitespec/core
  -> validate
  -> ResolvedSite
  -> @sitespec/astro
  -> component source contracts
  -> generated Astro source under .site/astro
  -> Astro static build
  -> rendered HTML contracts
  -> dist/
```

`@sitespec/astro` owns the Astro dependency and resolves Astro runtime subpath imports from its own package context. A generated website does not need to add `astro` as a direct dependency just to build or run dev; the renderer remains the framework boundary.

Page specs can use only registered sections. They cannot contain inline HTML, inline CSS, class names, token names, or JavaScript expressions.

## Core agent loop

Inside a generated site, agents use the project-local CLI pinned in `package-lock.json`:

```text
npm run site -- spec --json
  -> understand allowed pages/components/props/runtime
  -> edit Site Spec/content
  -> if necessary: npm run site -- add component <id>
  -> define the component contract before implementation
  -> npm run site -- validate --json
  -> fix deterministic diagnostics
  -> npm run build
```

## Portable agent contract

`sitespec init` generates a short `AGENTS.md` that is the repository bootstrap for coding agents. It does not duplicate the current component registry. Instead it teaches the agent how to discover the live project API:

```text
AGENTS.md
  -> npm run site -- spec --json
  -> current pages / components / props / capabilities / agent protocol
  -> edit source-of-truth files
  -> npm run site -- validate --json
  -> repair from structured diagnostics
  -> npm run build
```

`CLAUDE.md` contains only:

```text
@AGENTS.md
```

so the canonical instructions remain in one file. Codex/Cursor-style agents can consume `AGENTS.md` directly, while Claude Code receives the same contract through `CLAUDE.md`.

`npm run site -- spec --json` now contains a stable agent-facing section:

```json
{
  "agent": {
    "protocolVersion": "1",
    "workflow": {
      "inspect": "npm run site -- spec --json",
      "inspectTarget": "npm run site -- spec <page-or-component> --json",
      "validate": "npm run site -- validate --json",
      "build": "npm run build",
      "addComponent": "npm run site -- add component <id>"
    },
    "rules": {
      "preferExistingComponents": true,
      "pageUsesRegisteredSectionsOnly": true,
      "newComponentsViaCliOnly": true,
      "editGeneratedFiles": false,
      "fixAllValidationErrors": true,
      "buildBeforeComplete": true
    }
  }
}
```

The protocol is intentionally renderer-agnostic. Correctness depends on files + CLI + JSON, not on MCP, a vendor-specific skill, or model memory.

### Repair-oriented diagnostics

Machine diagnostics are designed as a recovery API rather than prose-only errors. For example, a misspelled component can return:

```json
{
  "code": "SECTION_COMPONENT_UNKNOWN",
  "actual": "feature-grdi",
  "allowed": ["cta", "feature-grid", "hero"],
  "suggestions": [
    {
      "action": "reuse-component",
      "candidates": ["feature-grid"]
    },
    {
      "action": "create-component",
      "command": "npm run site -- add component feature-grdi"
    }
  ]
}
```

Unknown props, variants, themes, content references, internal links, placement violations, and max-per-page violations expose the same structured repair fields where a deterministic repair exists. Human CLI output also prints the allowed values and repair actions.

```text
npm run dev      -> source/spec watcher + incremental renderer

```

## Development server

`npm run dev` is deliberately source-oriented. It does not call `npm run build` and it does not create or update `dist/`.

```text
site.yaml / pages / content / component contracts / tokens
  -> validate + resolve
  -> update generated .site/astro source
  -> Astro dev server + HMR
```

Draft pages are available in dev mode. When a source edit temporarily makes the project invalid, the process stays alive and existing routes render a diagnostic page that refreshes itself until the source becomes valid again. The terminal receives the same stable Site Spec diagnostics.

The watcher follows `site.yaml`, `pages/`, `content/`, `components/`, `shell/`, `design/`, and `public/`. Component implementation edits still flow through Astro/Vite HMR; spec/content/token edits regenerate only the renderer input under `.site/astro` and never run a production build.

For machine consumers, `--json` is a newline-delimited event stream rather than one long-lived JSON document:

```json
{"version":"0.1","event":"ready","url":"http://127.0.0.1:4321/","host":"127.0.0.1","port":4321,"valid":true,"diagnostics":[]}
{"version":"0.1","event":"updated","valid":true,"diagnostics":[]}
```

Preview never invokes the Site Spec parser, validator, resolver, or Astro renderer. At startup it performs one integrity check: it hashes the project source inputs (`site.yaml`, `pages/`, `content/`, `components/`, `shell/`, `design/`, and `public/`) and compares them with `.site/build.json` written by the last successful `npm run build`. If they differ, preview fails with `PREVIEW_BUILD_STALE` instead of showing an old build. After startup, HTTP requests are served exclusively from `dist/`.

Routing is intentionally static and SPA-free:

```text
/               -> dist/index.html
/pricing        -> dist/pricing/index.html
/pricing/       -> dist/pricing/index.html
/assets/app.css -> dist/assets/app.css
/unknown        -> dist/404.html (404) or a plain 404
```

Only `GET` and `HEAD` are accepted. Preview sends `Cache-Control: no-store`, prevents path traversal, does not expose `.site/`, and never falls back to `index.html` for an unknown route.


## GitHub Pages deployment

`npm run site -- deploy github-pages` follows the Git-native model rather than pushing production files from a developer laptop.

```text
npm run site -- deploy github-pages
  -> require Git repository root
  -> require package.json + exact @sitespec/cli version + package-lock.json
  -> detect origin GitHub repository
  -> detect deployment branch
  -> run a real local production build as preflight
  -> validate the GitHub Pages artifact
  -> create/update .github/workflows/site-pages.yml
  -> stop

commit / PR / merge / push
  -> GitHub Actions
  -> npm ci
  -> npm run build
  -> upload-pages-artifact
  -> deploy-pages
  -> GitHub Pages
```

The command deliberately does **not** run `git add`, create a commit, or push. This keeps deployment changes inside the same pull-request and review model as the rest of the site.

The generated workflow is managed and idempotent. Site Spec refuses to overwrite an existing `.github/workflows/site-pages.yml` unless that file carries the Site Spec managed marker. The workflow currently uses the GitHub-documented Pages flow:

```text
actions/checkout@v6
actions/setup-node@v7
actions/configure-pages@v5
actions/upload-pages-artifact@v4
actions/deploy-pages@v4
```

The generated workflow follows GitHub's documented token permissions:

```yaml
permissions:
  contents: read
  pages: write
  id-token: write
```

After `npm run build`, the workflow compares `.site/resolved.json` with `actions/configure-pages`' actual `base_url`. A mismatch fails before artifact upload, preventing incorrect canonical URLs or base paths from reaching production.

GitHub Pages must be configured to use **GitHub Actions** as its publishing source once per repository. The generated workflow then deploys on every push to the selected branch and also supports `workflow_dispatch`.

### Repository URL and base path

A project repository such as `octocat/acme` is normally served from:

```text
https://octocat.github.io/acme
```

Therefore its `site.yaml` must use that production URL unless a custom domain is configured:

```yaml
site:
  url: https://octocat.github.io/acme
```

The renderer derives the deployment base path from this URL. For the example above, Site Spec renders internal root-relative `href` and `src` values under `/acme` and gives Astro the same base path, so both component links and generated `_astro` assets work on GitHub project Pages.

A user/organization Pages repository named `octocat.github.io` uses the root URL instead:

```text
https://octocat.github.io
```

Reserved development domains such as `.test` are rejected by `npm run site -- deploy github-pages`. If `site.url` uses another public host, Site Spec treats it as a custom domain and reminds the user to configure that domain in GitHub Settings > Pages. A repository `CNAME` file by itself is not treated as GitHub Pages configuration.

### Deployment artifact rules

The command performs a local build before changing the workflow. It then rejects artifacts containing symbolic links, hard links, or more than 10 GB of files, matching GitHub Pages artifact constraints. This makes provider-specific deployment failures visible before a PR is merged.


> **Astro test isolation:** the core test suite runs Node test files with `--test-concurrency=1`. Astro's programmatic static build uses transient prerender state under `.astro/.prerender`; parallel builds from multiple test workers can race on that state. SiteSpec still keeps Astro and Vite caches project-local under `.site/`.
